## Stack

- Backends, chosen by environment variables and all defaulting to the no-container setup: database (SQLite | PostgreSQL), objects (`STORAGE_BACKEND=fs` | `s3`), jobs (`JOBS_MODE=eager` | `thread` | `external`), sandbox (`SANDBOX_BACKEND=docker` | `podman` | `remote` | `none`)

## Build & Test
- Install: `npm install` at the repo root (npm workspaces include `apps/web`). Do NOT use pnpm/yarn
  and never add dependencies to the root `package.json`; add web deps with
  `npm install <pkg> --workspace apps/web`, API deps in `apps/api/pyproject.toml` (or the owning package).
- Test everything: `npm test` (api pytest, then web vitest)
- API only: `cd apps/api && uv run --all-packages pytest`
- **Slow suites vs. the Bash tool limit:** a Bash call is killed after 2 minutes unless you pass a
  longer `timeout` (max 600000 ms). The full API suite (~4.7k tests) takes 2–4 minutes and the web
  suite ~2 minutes, longer while other agents share the machine. Run the tests of what you changed
  (`uv run --all-packages pytest src/app/modules/<module>`, `npx vitest run src/features/<feature>`);
  if you need a full suite, call Bash with `timeout: 600000` (a shell `timeout 590` prefix does not
  extend the tool's limit). Three tool-killed commands in a row end the attempt (`agent_command_stuck`).
  The acceptance gate runs the full `npm test` anyway.
- Run API: `cd apps/api && uv run python -m app` (serves `create_app` on HOST/PORT, default 127.0.0.1:8000; set FORWARDED_ALLOW_IPS to honour proxy headers)
- Web only: `npm test --workspace apps/web`
- Browser journeys: `npm run test:e2e` (Playwright, not part of `npm test`)
- System tests: `npm run test:system` (`tests/e2e/`, not part of `npm test`): starts the shipped
  programs (`python -m app`, `app.worker`, `app.sandbox_service`, `app.migrate_backend`, the admin
  commands, `next build` + `next start`) as processes and drives them over HTTP; about three
  minutes, `-- -m "not web"` skips the Next.js build. Run it after changing anything that wires
  processes together (composition root, settings, worker, storage, sandbox, migration, compose)
- **Opt-in commands outside `npm test`.** `npm test` needs no containers, network or cloud credentials
  (SQLite, `STORAGE_BACKEND=fs`, eager jobs). These do, so they are never part of it; run one only
  when your change touches what it covers:
  - `npm run test:pg` — the whole API suite against PostgreSQL 16 + pgvector in a throwaway
    podman-compose (or `docker compose`) container; extra arguments go to pytest
    (`npm run test:pg -- -k ledger`); `TEST_DATABASE_URL` set means "use that server, start nothing"
  - `npm run stack:up` — build the images and start the local stack from `compose.yaml` (web, api,
    worker, PostgreSQL, MinIO, Mailpit); companions `stack:down`, `stack:logs`, `stack:reset`
    (`reset` deletes the volumes)
  - `npm run stack:smoke` — with the stack up: wait for `/readyz` and the web app, then a blob round
    trip through S3 and a job run by the separate worker
  - `npm run infra:check` — `tofu fmt -check` and `tofu validate` of everything under `infra/`, no
    cloud credentials; needs `tofu`
- Running and deploying (every environment variable by backend, the stack, the worker and sandbox
  processes, `python -m app.migrate_backend`, the OpenTofu staging walkthrough): `docs/deploy.md`;
  variables with placeholders: `.env.example`

## How work reaches claw-forge

Feature and bug work in this project goes through claw-forge, not
hand-written edits: the parallel agents rely on file-claim locks, the
acceptance gate and merge-gating, and hand edits bypass all three.

- **New feature or capability** → the `claw-forge-feature` skill
- **Something broken, failing, or regressed** → the `claw-forge-bug` skill
- **Checking or controlling a live run** → the `claw-forge-ops` skill

Trivial changes — a typo, a rename, a config value, a one-function fix —
do not need a spec. Make them directly.

**A spec must validate with zero errors and zero warnings before
`claw-forge plan`.** Use `claw-forge validate-spec --json <spec>` and read
`clean`; `passed` counts errors only. INFO findings never block.

**Never run `claw-forge run` without asking.** It dispatches parallel
agents, writes to git and runs unattended for hours.
