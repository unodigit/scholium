# Paper AI (the AI pre-review tab)

`AiTab` is the paper page's AI pre-review margin tab (docs/design.md §5.2):
the purple `--ai` panel with the fixed banner, findings grouped by agent, and
the Rebut / Confirm / Wrong buttons.

```tsx
import { AiTab } from "@/features/paper-ai";

<AiTab paperId="sch:k3f9-q2xz-7mwd/v2" />
```

`/ai/k3f9-q2xz-7mwd/v2` (and `/ai/k3f9-q2xz-7mwd` for the newest version)
shows the same tab on a page of its own. The URL mirrors the paper page's
`/p/{id}[/v{n}]`; the `sch:` prefix is optional. The page only reads the URL;
the report is fetched by the tab in the reader's browser, and the first HTML
already carries the advisory banner.

## What it shows

```text
┌────────────────────────────────────────────────┐
│ ▎Advisory. Generated by AI agents. Not a peer  │  ← the fixed banner, --ai
│   review.                                      │
│ Version 2 · 3 findings                         │
│ ────────────────────────────────────────────── │
│ Methodology                                    │
│ 1 finding                                      │
│ ▎The baseline is never described precisely…    │  ← purple left border
│ Major · Confidence: medium                     │
│ Quoted from the paper: “we compare against…” ↗ │  ← jumps to the span
│ [Rebut] [Confirm] [Wrong]                      │
│ ┌ Author rebuttal ───────────────────────────┐ │
│ │ Section 3.2 names the baseline and its seed│ │
│ └────────────────────────────────────────────┘ │
│ ✓ Confirmed by a reviewer                     │  ← icon + word, never colour
│ Integrity · Reproducibility · Literature …     │
│ ▸ How this was generated                      │
└────────────────────────────────────────────────┘
```

- **The banner is fixed.** It renders on every state — loading, missing,
  failed — because it qualifies everything below it, and always with the
  design's own words (§8): a `label` a node re-worded never reaches the
  reader.
- **Findings group by agent.** All four specialists always appear (the
  pipeline always runs all four; the endpoint sends an empty group for a
  quiet one), so "no findings" reads as a result, not a gap. An agent nobody
  knows keeps its own group after the specialists.
- **Every finding shows its evidence.** A quoted span links to the paragraph
  it was copied from (`#p-{paragraph_id}`, the anchor the reading column
  gives its paragraphs); a `ref:` id or a sandbox log line is shown in
  monospace, not as a dead link.
- **The buttons are for people.** *Rebut* opens the authors' reply form;
  *Confirm* / *Wrong* post a reviewer's verdict. Who may press which is the
  API's call (the trust tier lives inside a short-lived token): a signed-out
  visitor is told to sign in without a request being made, and a reader the
  API refuses hears the API's own words ("Only a paper author may rebut an AI
  finding."). A posted answer is followed by a reload, so the reply and the
  verdict appear beside their finding the way the report serves them.

## Advisory means advisory (§1)

- The panel is the one place in the app that may use `--ai`, the reserved
  colour of the AI pre-review. It carries the banner fill, the panel edge and
  the finding cards' left border — never a word: `--ai` on `--ai-soft` is
  below 4.5:1 at 13 px, so the banner's text is `--ink`.
- Severity is a plain word (`Major`), not a chip: an AI report must not read
  as a human status, so no status colours touch it.
- A reviewer's confirmed/wrong verdict is the one human colour here, and only
  on its icon; the word carries the meaning (never colour alone, §9).

## Where the data comes from

`GET /v1/papers/{id}/ai-reviews` (feature 122), read anonymously and
uncached. `paperId` is any spelling the catalog accepts — `sch:` id, version
id (`sch:…/v2`) or bare short id; a version uses the version's own route
(`/v{n}` is one segment). Answers post to `POST /v1/ai-reviews/{cid}/rebuttal`
and `POST /v1/ai-reviews/{cid}/assessments` (feature 123) through the shared
API client, which attaches the signed-in account's bearer token and refreshes
it once on a 401.

A `404` — the paper is not on this node, or its review has not been written
yet — is the calm empty state, not an error: one sentence and a way to the
paper. Transport failures are retryable and say so in one plain sentence.

`parseAiReport` never throws: the endpoint may grow fields and a half-built
node may serve fewer, so whatever cannot be recognised degrades to a neutral
label rather than a blank panel.

## Accessibility

- The banner is a `role="note"`; the loading line and the friendly sign-in
  note are polite live regions; refused answers are `role="alert"`.
- Buttons are at least 44 px; the evidence link is a real link with its
  destination in words ("jumps to the quoted paragraph" for screen readers).
- Long claims, quotes, ids and errors wrap (`overflow-wrap: anywhere`)
  instead of overflowing the 360 px panel; ids are monospace.
- Colour is reinforcement only: forced-colours and reduced-motion are
  handled; nothing depends on telling purple from grey.

## Files

| File | Responsibility |
| --- | --- |
| `ai-tab.tsx` | The component: banner, groups, finding cards, actions, provenance. |
| `ai-tab.css` | Styles; every value is a design token, and the one `--ai` sheet in the app. |
| `ai-report.ts` | The report's shape, tolerant parsing of the endpoint's payload, display copy. Pure. |
| `ai-api.ts` | The three endpoints, error classification, calm failure copy. |
| `index.ts` | Public surface for the paper page. |
| `*.test.ts(x)` | Parsing, endpoints, the component's every state and action, CSS contract, route. |
| `app/(paper-ai)/layout.tsx`, `paper-ai.css` | Global nav + page shell for `/ai/…`. |
| `app/(paper-ai)/ai/[...ref]/page.tsx` | The `/ai/{id}[/v{n}]` route: metadata, URL parsing, bad-id notice. |

The node's API is cross-origin from the web app: the browser calls
`NEXT_PUBLIC_API_URL` directly, as the Submit wizard and the Proof tab do, so
the node must allow the web origin (or be served from the same origin).
